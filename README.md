# Go Gateway Starter

A deliberately minimal, extensible API gateway in Go. It uses `net/http`, `httputil.ReverseProxy`, and ordinary HTTP middleware. No third-party dependencies.

This code is a prototype for exploring how the parts interact. It will be replaced by a rewrite; see the [roadmap](docs/roadmap.md) and [ADRs](docs/adr/README.md) for the intended direction.

## What it does

- Forwards all `/api/` requests to a configurable HTTP upstream, keeping the original path and query.
- Supports global and per-route middleware using `func(http.Handler) http.Handler`.
- Creates shared request context before registered middleware runs.
- Supports optional request, outbound-request, upstream-response, and completion hooks.
- Includes middleware-only (`extensions/headers`), shared-state (`extensions/requesttag`), access-log (`extensions/accesslog`), and outbound-signing (`extensions/outboundsign`) examples.
- Validates route configuration and shuts down gracefully.
- Includes integration tests with a local `httptest` upstream.

## Run it

From the project directory, start the sample upstream in one terminal:

```text
go run ./cmd/upstream
```

Start the gateway in a second terminal:

```text
go run ./cmd/gateway
```

Send a request through the gateway:

```text
curl -i 'http://localhost:8080/api/hello?q=1'
```

The response should contain `X-Gateway: starter`, a generated `X-Request-ID`, and JSON generated by the upstream. The gateway logs a completion record with HTTP accounting and gateway metadata.

Run the tests:

```text
go test ./...
```

To change the upstream or listening address, use Nushell environment variables before starting the gateway:

```nu
$env.GATEWAY_UPSTREAM = 'http://127.0.0.1:9999'
$env.GATEWAY_LISTEN_ADDR = ':8081'
go run ./cmd/gateway
```

## Extend it

Make any middleware by writing a function of type `func(http.Handler) http.Handler`.
Use `gateway.New(routes, globalMiddleware...)`, and attach route-specific middleware with `Route.Middlewares`.

For lifecycle extensions, use `gateway.NewWithConfig`:

```go
access := accesslog.New(accesslog.Config{
    Report: func(record accesslog.Record) {
        slog.Info("request completed",
            "request_id", record.RequestID,
            "status", record.StatusCode,
            "result", record.Result,
            "duration", record.Outcome.Duration,
            "has_error", record.Outcome.Err != nil,
            "has_response_error", record.ResponseError != nil)
    },
})
app, err := gateway.NewWithConfig(gateway.Config{
    Routes:      routes,
    Middlewares: []gateway.Middleware{access.Middleware},
    Extensions:  []any{access},
})
```

Here `accesslog` is `example.com/go-gateway-starter/extensions/accesslog`. The demo uses it as the main lifecycle extension. `extensions/requesttag` remains a standalone shared-state example, but is not registered by the demo.
Middleware and hook registration are explicit and independent. Each extension implements only the interfaces it needs: `RequestHook`, `BeforeUpstreamHook`, `UpstreamResponseHook`, or `CompletionHook`. Extensions are shared across concurrent requests, so instance fields and completion callbacks must be concurrency-safe. Nil extensions and extensions implementing no hooks are rejected at startup.

### Execution and errors

```text
Create RequestContext and attach it to the standard context
  Global middleware: before
    Request hooks
    Router
      Record route metadata
      Route middleware: before
        Select configured upstream and rewrite request
        BeforeUpstream hooks on the rewritten outbound request
        Proxy request
        Upstream response hooks
        Stream response
      Route middleware: after
  Global middleware: after
Completion hooks
```

Hooks run in registration order, including completion hooks. A request, outbound, or response hook error stops that phase. Return `&gateway.HTTPError{StatusCode: 403, Message: "denied"}` for a controlled rejection. Other request-hook errors produce a generic 500; outbound-hook, proxy, and upstream-response-hook errors produce a generic 502. A wrapped `*http.MaxBytesError` from request-body reading receives a generic 413. Error details remain in `Outcome.Err`, not the response. Normal upstream HTTP error statuses are forwarded and are not Go errors.

Completion runs once per gateway invocation after the middleware chain unwinds, even if middleware rejects, routing misses or redirects, or handling panics. Registered middleware must call `next` synchronously and at most once. Middleware that returns while downstream work continues (such as `http.TimeoutHandler`) is outside this experiment's lifecycle contract. Completion hooks must not panic or write a response. They receive the gateway entry context, which may already be canceled, rather than contexts derived inside middleware. Panics, including streaming aborts, continue to propagate.

`Outcome` reports duration, observed gateway errors, and whether the middleware chain aborted. It does **not** promise successful client delivery or capture response status/bytes. Streaming failures after headers are committed may set `Aborted` without setting `Err`. Response-observing middleware can provide HTTP accounting; the core leaves `ResponseWriter` and its optional interfaces unchanged.

### Shared request state

Call `gateway.FromContext(r.Context())` in middleware to retrieve the same `*RequestContext` passed to hooks. Metadata is gateway-owned: `StartedAt()`, `RoutePrefix()`, and `Upstream()` expose timing and available routing information. The upstream accessor returns a copy. Route middleware sees the matched route before proxying, but no upstream has been selected yet.

Use a private typed key for extension state:

```go
var identityKey = gateway.NewStateKey[string]()

// In middleware, before calling next:
rc, ok := gateway.FromContext(r.Context())
if ok {
    gateway.SetState(rc, identityKey, "example-user")
}

// In a hook:
identity, found := gateway.GetState(rc, identityKey)
```

Distinct keys are isolated, even when their value types match. Stored nil values are distinguishable from missing values. Request context access is not synchronized: hooks run serially, and extensions must not access the context concurrently or retain it after completion. Standard contexts still own cancellation, deadlines, and trace propagation. Middleware must derive contexts from the incoming request context, not replace them with an unrelated context.

Only middleware registered with the gateway can access its context before calling `next`. Middleware wrapping the gateway externally cannot see it on entry.

This project supports **compile-time extensions**. It intentionally does not provide dynamic plugin loading, a control plane, databases, authentication, rate limiting, or quotas yet.

## Observability experiment

`extensions/accesslog` combines HTTP middleware with response and completion hooks, without changing the core API. The demo uses it to report generated request IDs, route/upstream selection flags, upstream and downstream statuses, response-body byte counts, duration, safe error-kind labels, and gateway outcomes. It distinguishes local rejection, normal upstream HTTP errors, proxy execution errors, and aborted responses.

Trace correlation is optional: provide `accesslog.Config.TraceID` and register tracing middleware before access-log middleware. The extension snapshots the trace ID from the derived context rather than expecting completion to inherit that context. No tracing SDK is installed by the demo.

See [the access-log experiment](extensions/accesslog/README.md) for registration, middleware order, classification limits, and findings. Tests cover partial writes, streaming aborts, flushing, informational responses, protocol upgrades, and concurrent request isolation. HTTP accounting remains extension-owned; the gateway's `Outcome` is unchanged.

## Outbound-signing experiment

`extensions/outboundsign` uses route middleware to install a private signing key and a `BeforeUpstreamHook` to sign the rewritten request's method, destination, effective Host, and escaped URI. A private transport wrapper provides the fallible boundary after `ReverseProxy.Rewrite`. On a hook error, it closes the outbound body and skips later outbound hooks and transport execution; completion still runs after middleware unwinds.

The integration tests verify signatures at a local upstream, including upstream base-path and query rewriting, client-signature replacement, unchanged request bodies, signing failures, cancellation, and concurrent routes with different keys. No route-matched hook was needed. The demo executable does not enable signing.

See [the outbound-signing experiment](extensions/outboundsign/README.md) for registration and limits. This is not a production authentication protocol: bodies are not signed and replay protection is absent. The hook API remains experimental.

## Proxy safety boundaries

This is a focused hardening baseline, **not production readiness**. Ownership is explicit:

| Owner | Protection / configuration |
| --- | --- |
| Framework | Standard `ReverseProxy` hop-by-hop handling; rebuild standard forwarding headers from the immediate peer; discard client `X-Real-IP`; preserve streaming, cancellation, and writer capabilities |
| Embedding application | Supply a reusable `Config.Transport` for connection, TLS, response-header, and pool policy; configure the inbound `http.Server` |
| Optional middleware | [Request-body limits](extensions/bodylimit/README.md) and [fail-fast admission](extensions/admission/README.md), applied globally or per route without buffering |
| Optional transport package | [Direct upstream origin/IP restrictions](extensions/egress/README.md), enabled only with explicit deployment allowlists |
| Example executable | Explicit transport/server/header settings, an 8 MiB body limit on `/api/`, 64 active downstream calls with no admission queue, source-only diagnostics, and allowlisted completion-log fields |

### Forwarding-header trust

`Rewrite` uses `SetURL` and `SetXForwarded`. Client `Forwarded`, `X-Forwarded-For`, `X-Forwarded-Host`, and `X-Forwarded-Proto` are removed, not appended or trusted. `X-Real-IP` is also discarded. The outbound values describe the immediate connection: peer IP, inbound Host, and TLS state. The inbound Host is client-controlled, not a validated identity. Behind another proxy these values describe that hop, not the original client. Trusted-chain reconstruction and Host validation require deployment-specific policy, not a blind copy of inbound headers. Other vendor-specific identity headers are not comprehensively filtered.

Standard hop-by-hop headers and `Connection`-nominated headers are stripped in both directions. Go preserves the protocol exceptions for `TE: trailers` and upgrades. Trusted compiled-in outbound/response hooks run after this sanitation and must not reintroduce unsafe headers. Tests cover spoofed duplicate headers, Connection-nominated fields, end-to-end headers, trailers negotiation, and existing upgrade behavior.

### Transport and timeout ownership

`Config.Transport` is shared by all routes, including when outbound hooks are enabled. Configure it once before serving; the caller owns its lifetime and `CloseIdleConnections`. Nil retains `http.DefaultTransport` for compatibility, including its environment-proxy behavior and lack of a response-header timeout. The framework neither creates per-request transports nor imposes a universal stream deadline.

`cmd/gateway` clones the standard transport once and disables ambient HTTP proxy variables. Its example policy is:

- Dial timeout: 3s; TCP keepalive: 30s; TLS handshake timeout: 5s.
- Response-header timeout: 10s; expect-continue timeout: 1s.
- Idle-connection timeout: 90s; maximum idle connections: 100 overall / 16 per host; maximum connections per host: 64.
- Inbound header-read timeout: 5s; inbound idle timeout: 60s. No blanket `ReadTimeout`, `WriteTimeout`, or total request deadline.
- Native inbound request-header and upstream response-header budgets: 64 KiB each. These use Go's parser/protocol semantics, not an exact universal wire-byte ceiling.

These are source-level example settings, not new framework defaults or environment configuration. Response-header timing starts after the request body is written; it does not bound slow uploads, pool queue waits, or response-body duration. Idle timeouts do not limit active streams. Request contexts cancel dial/queue/transport work and streaming copies; a cancellation after response commitment can abort rather than replace the response. Completion still means handling ended, not successful delivery. Tests exercise timeout failures, connection reuse, streaming beyond the header budget, incremental uploads, and real client disconnects before and after response headers.

### Admission and resource limits

[`extensions/admission`](extensions/admission/README.md) bounds concurrent calls to downstream handlers with no waiting queue. The example registers one shared 64-call budget after access-log middleware. Saturation receives a generic local 503 before request hooks/routing; completion and HTTP accounting still run, without inventing an upstream error. Slots remain occupied during uploads, response streaming, and transport-pool waits until downstream returns or unwinds, including after cancellation/panics. Request and writer capabilities are unchanged.

This counts HTTP/2 streams independently of connection-pool limits. It is not a request-rate policy or a cap on every process goroutine/socket: outer middleware, completion reporters, rejection writes, pre-handler work, and server cleanup remain outside the budget. Stalled or healthy long-lived streams can occupy every slot. Inbound header rejection occurs before gateway entry and therefore has no gateway completion event. Upstream header-parse failures use the existing generic 502 path.

Slow-upload, slow-reader, accepted-connection, and workload-isolation policies remain deployment-owned. No blanket stream-duration or body-idle deadlines were added. See [the resource-limit assessment](docs/investigations/resource-limits.md) for established protections, tests, and the remaining slow-body decisions.

### Optional destination restrictions

[`extensions/egress`](extensions/egress/README.md) uses `Config.Transport` to enforce explicit allowed HTTP(S) origins and IP networks. It validates every DNS answer before dialing validated IP literals, while preserving HTTP/TLS identities and connection reuse. It owns a clean transport so ambient proxies and template dial/protocol callbacks cannot bypass these checks. This package is opt-in; the demo does not infer permitted deployment networks or enable it automatically. No core lifecycle API or default destination policy changes.

### Sensitive diagnostics

The framework's private `ReverseProxy.ErrorLog` emits source-only structured warnings via `slog.Default()`, not raw standard-library diagnostic text. Original errors remain unchanged in `Outcome.Err` and extension records. No process-wide logging configuration is changed by constructing a gateway.

The example executables explicitly install JSON logging, source-only `http.Server` diagnostics, and a source-only global standard logger. The last boundary also covers transport diagnostics that bypass proxy/server loggers. The gateway example omits raw paths, origins, route labels, trace IDs, configured listen/upstream values, and error strings from its own sinks; methods/results use known labels. This loses diagnostic detail by design. Embedders own server/process log configuration and all custom sinks. See [the diagnostic audit](docs/investigations/sensitive-diagnostics.md) for protections, tests, and remaining gaps.

### Remaining risks

The [follow-up plan](docs/investigations/proxy-risk-follow-ups.md) records five focused passes, ownership, verification, and deferred work.

- **Destination restrictions:** default framework validation still only requires an HTTP(S) URL with a host. Without the optional egress transport there is no origin/IP allowlist or connection-time validation. With it, deployments must still choose narrow origin/network lists, apply network-level egress controls, and handle connection retirement and network translation. Static configuration is trusted, not a complete SSRF defense. Compiled-in extensions, callbacks, and custom transports are trusted code, not sandboxed.
- **Sensitive data:** generic framework failures hide error details from clients, but `HTTPError.Message` is explicitly public. `Outcome.Err`, access-log records, constructor errors, extension callbacks, and panic values remain sensitive internally. Custom sinks, application-created servers/loggers, runtime crash output, and debug facilities need deployment review. Source-only proxy diagnostics and the example process log policy do not make arbitrary records safe to serialize or provide a complete redaction policy.
- **Resource and operational limits:** admission bounds downstream calls, not slow rejection writes, server body draining, completion reporters, or accepted sockets. Slow request/response bodies, idle active streams, aggregate resource usage, workload isolation, decompression, TLS termination, graceful termination of long-lived streams/upgrades, and load behavior still need application-specific review. Header budgets use native Go semantics; body limits are streaming read limits, not all-or-nothing upload validation. Keep Go patched; using the standard proxy does not remove protocol/security maintenance.

## Boundaries to revisit later

- Inbound middleware wraps `http.Handler` and can reject requests before proxying.
- Gateway-owned upstream URL rewriting belongs in the reverse proxy's `Rewrite` hook. Fallible outbound-header customization runs afterward through `BeforeUpstreamHook`.
- Upstream response hooks use `ReverseProxy.ModifyResponse`; local responses do not run them. Forwarded informational responses are outside this hook, except protocol upgrades (101).
- Outbound hooks run once per proxy round trip, not per transport-internal retry or connection attempt. Register signing after hooks that modify signed fields; the transport may still add protocol headers and choose wire framing. Hooks must preserve context and body ownership. Replaceable upstream selection remains deferred.
- Route-specific hooks, live-span annotation, exact proxy-error phases, asynchronous middleware, and response-body transformations need concrete use cases before expanding the public API.
- Production use will require configuration management, security review, TLS, workload-specific limits/timeouts, reliable telemetry, and broader protocol/load verification beyond the protections above.

The exported API is intentionally experimental; rename the module path before publishing.
