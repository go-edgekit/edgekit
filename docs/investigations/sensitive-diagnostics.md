# Sensitive diagnostic boundaries

**Status:** Focused implementation assessment, not an architecture decision or a complete redaction policy

This is pass 2 of [the risk follow-up plan](proxy-risk-follow-ups.md). No ADR statuses, lifecycle hooks, core outcomes, or signing error semantics change.

## Audit and established protections

| Sink | Policy |
| --- | --- |
| Framework proxy/hook error handling | Keep original errors in `Outcome.Err`; do not automatically log them. Generic client failures remain generic. `HTTPError.Message` remains explicitly public. |
| Framework `ReverseProxy.ErrorLog` | Replace each diagnostic write with a static structured warning: `msg="diagnostic details omitted"`, `source="reverse_proxy"`. Never forward diagnostic text. |
| Example `http.Server.ErrorLog` | Use the same source-only adapter, with `http_server` or `upstream_http_server`. Panic values, stacks, peer addresses, and malformed header values are omitted. |
| Example process-wide standard logger | Emit source-only `stdlib` events. Some standard transport/HTTP2 diagnostics bypass proxy/server `ErrorLog`; examples cover this fallback without modifying global logging from the framework. |
| Example startup/serve/shutdown logs | Use static messages and allowlisted error-kind labels. Do not print raw configured upstream/listen strings or arbitrary error text. The demo upstream's fixed `:9090` label is not configuration data. |
| Example completion sink | Log validated generated request IDs, allowlisted method/result labels, numeric HTTP observations, timing, flags, and safe error-kind labels. Omit raw paths, origins, route labels, trace IDs, and errors. |
| Access-log extension and other callbacks | Keep original records and errors unchanged. A callback remains responsible for its own output; records are not declared safe to serialize wholesale. |

The shared adapter is `internal/safelog`, an implementation detail rather than a new public logging API. It emits to `slog.Default()`. The framework installs only its private proxy logger: constructing a gateway does not replace the application's process-wide logging configuration. Both example executables explicitly install a JSON `slog` handler writing directly to stderr, then route the standard logger through the source-only adapter. The direct sink avoids a standard-log/slog recursion loop. Configure this once at startup, before serving.

Applications embedding the framework own their `http.Server.ErrorLog`, standard logger, structured handlers, and all other sinks. The internal helper is not an importable extension contract. Setting a new global logger later can change or bypass the example policy and requires another audit.

## Why messages are omitted rather than scrubbed

Arbitrary standard-library messages can contain URLs, credentials, headers, body excerpts, panic values, stacks, and future formats. A keyword or regular-expression filter cannot reliably find every secret. The adapter does not parse, retain, or forward input text, including unfamiliar messages. Empty writes emit no event.

This deliberately sacrifices diagnostic detail. Events are coarse signals that a component emitted a diagnostic, not one-per-request accounting, exact failure-phase facts, or proof of client delivery. Source labels are static code constants. Logging remains synchronous and does not add response-writer wrapping or change request completion. Applications may configure structured sinks and extension callbacks for additional approved fields, but there is no raw-debug switch in this pass.

## Error and completion interpretation

`ErrorKind` is sink-owned interpretation based on error identity/type: `none`, `canceled`, `deadline_exceeded`, `timeout`, or `other`. It does not format the error or establish why a request failed. Method labels are the standard HTTP methods or `OTHER`; result labels are the known access-log results or `unknown`. These are log-only normalizations, not changes to the forwarded request.

Only IDs generated by the access-log middleware belong in the example request-ID field. The sink also validates its 32-character lowercase hexadecimal shape; shape checking alone is not proof that an arbitrary externally supplied ID is safe. Trace IDs need a separate approved extraction/validation policy before a deployment logs them.

Original causes remain accessible with `errors.Is`/`errors.As`. A stream can log a proxy diagnostic and abort after partial output without setting `Outcome.Err`, because standard response-copy failures do not necessarily enter the proxy error callback. Panic unwinding and completion still happen before `net/http` handles a panic. The adapter neither recovers a panic nor invents an execution error. `http.ErrAbortHandler` retains its normal no-server-diagnostic behavior.

## Regression coverage

Tests inject credentials, paths, query tokens, authorization-like text, body excerpts, unknown messages, invalid UTF-8, and multiline panic/stack text. They exercise real proxy response-copy failures and real server panic/header diagnostics, plus normal and abort-only paths. They verify body closure, partial responses, unchanged original errors, once-only completion after middleware unwinds, concurrent diagnostic writes, safe global standard-log fallback, and the absence of process-global logging changes from gateway construction. An error whose `Error()` method panics verifies that the error classifier does not format arbitrary errors.

## Remaining risks and operational work

- Custom middleware, extension reporters, tracing/exporter integrations, custom transports, TLS key-log writers, and application-created loggers can still write secrets. `Outcome.Err`, access-log snapshots, constructor errors, and panic values remain sensitive data internally.
- An explicit `HTTPError.Message` is a public response contract, not an automatic redaction surface. Upstream response bodies/headers and the demo upstream's request echo are not log redaction surfaces either.
- The library cannot intercept every process-global transport diagnostic without taking ownership of application logging. Embedders must configure those sinks; the example executables do so explicitly.
- Runtime crashes, fatal panics outside the HTTP server's recovery boundary, direct stderr/stdout writes, external crash reporting, packet capture, and environment-enabled diagnostic facilities may bypass these adapters. Disable sensitive debug facilities and audit the exact Go/runtime/deployment settings.
- Coarse logs reduce troubleshooting detail. Agree on approved identifiers, retention/access controls, bounded sink behavior, and a separate protected debugging process before deployment. This pass does not provide durable reporting, sampling, log-volume limits, or a complete production-security review.
